# Требования и допущения
**Статус:** рабочие гипотезы; не официальное ТЗ.

| ID | Требование кейса | Проверка |
|---|---|---|
| R1 | Анализ обращений | Macro F1, error analysis |
| R2 | Поиск повторений | Pairwise F1, false merges/false splits |
| R3 | Передача product team | Correct routing, acceptance, TTAI |
| R4 | Agent, prompt, tools | Tool contract and safety tests |
| R5 | Integration and feedback | Auditable approval/rejection workflow |
| R6 | Экономический эффект | Controlled timings, expenses, sensitivity |

**Подтверждено формулировкой:** много цифровых продуктов, анализ тикетов, повторы, передачa командам, prompt/tools, интеграция, feedback и оценка эффекта.

**Не подтверждено:** точный ITSM, объём заявок, лейблы датасета, бюджет, критерии оценки, допустимость внешних API, on-prem требования, может ли команда проводить пилот с сотрудниками поддержки. Слова «код опционален» и «дадут малый датасет» — пересказ встречи, проверить.

## Наставникам
1. Какая система поддержки, текущий процесс эскалации и маршрутизации?
2. Какие поля и связи (linked incidents, product, owner, timestamps) в датасете?
3. Какие KPI бизнеса приоритетны? Есть ли baseline?
4. Какие ограничения на модели, размещение, данные и права интеграции?
5. Можно ли привлечь support specialists к временному эксперименту?
6. Какие официальные критерии оценки и обязательные deliverables?

Договорённости превращать в ADR с датой, автором и evidence, а не незаметно заменять гипотезы фактами.
