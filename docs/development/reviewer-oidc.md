# ProductPulse reviewer identity: OIDC / Keycloak integration boundary

**Implemented and integration-tested with synthetic signed JWTs:** FastAPI OIDC bearer verification, server-scoped pair-review and lead-approval API, PostgreSQL persistence, signature/role/tenant checks.  
**Not yet implemented:** browser OIDC login via Auth.js, live Keycloak realm/provisioning, enforced organization-controlled multifactor authentication, full evidence review interface, automatic data redaction.

## Open source to reuse

Use an existing OIDC provider (for example [Keycloak](https://www.keycloak.org/)) and **PyJWT[crypto]** at the backend. Do not create a bespoke account database, password reset, JWT token issuer or signing key store.

Configure IdP access tokens with:
- RS256 signature and JWKS discovery;
- issuer \`iss\` matching the realm and an \`aud\` containing \`productpulse-review-api\`;
- a stable unique non-empty subject \`sub\`;
- a scope-specific \`tenant_scope\` claim, provisioned by the trusted identity provider;
- \`roles\` **as an array** containing \`productpulse_reviewer\` or \`productpulse_review_lead\`. Real Keycloak role mappings often use \`realm_access.roles\`; explicitly map them to \`roles\`, not trust arbitrary browser-supplied roles.

Backend environment example (never copy placeholder to a public deployment without configuring a real IdP):

\`\`\`sh
export PRODUCTPULSE_OIDC_ISSUER="https://id.example.org/realms/productpulse"
export PRODUCTPULSE_OIDC_AUDIENCE="productpulse-review-api"
export PRODUCTPULSE_OIDC_JWKS_URL="https://id.example.org/realms/productpulse/protocol/openid-connect/certs"
\`\`\`

Also provide \`DATABASE_URL\`, \`PRODUCTPULSE_SCOPE_ID\`, and \`PRODUCTPULSE_INTERNAL_TOKEN\` as in [API setup](internal-api-local.md). OIDC inputs are all-or-nothing: omitting any one setting fails backend startup.

## Internal service contract

Existing protected endpoints retain the internal service token. Review routes additionally demand **OIDC Bearer access token**:

\`\`\`text
GET  /internal/v1/reviews
POST /internal/v1/reviews
POST /internal/v1/reviews/approve
\`\`\`

Review JSON: \`ticket_key_a\`, \`ticket_key_b\`, \`label\` (one of same_incident / related_topic / different_incident / uncertain), \`rationale\`, \`operation_key\`. Reject extra fields, including \`reviewer_id\`, \`reviewed_at\`, \`tenant_scope\`, \`role\`; these are taken from verified identity or generated by backend clock.

Lead JSON: \`ticket_key_a\`, \`ticket_key_b\`, \`reason\`, \`operation_key\`. Third independent \`productpulse_review_lead\` must approve a pair in \`ready_for_lead\`; it **does not merge Problems automatically**.

A browser must NEVER store or access \`PRODUCTPULSE_INTERNAL_TOKEN\`. Auth.js + OIDC at the server-side BFF must obtain/forward the validated user's **access token** through server-only calls while protecting the user's session. Do NOT forward a frontend-provided \`reviewer_id\` or use the demo shared Basic Auth password as independent identity.

## How to verify

\`\`\`sh
python -m pip install -e ".[dev,storage,api,review]"
export PG_REGISTRY_TEST_URL="$DATABASE_URL"
alembic upgrade head
python -m pytest -q tests/incident/test_review_workflow.py tests/api/test_reviewer_auth.py tests/api/test_review_routes.py
\`\`\`

CI uses PostgreSQL 16, verifies two real concurrent DB transactions, and creates synthetic locally signed RSA JWTs. **This does not exercise the remote Keycloak login journey or certify enterprise access controls.**

## Go-live blockers

Need real IdP provisioning, PKCE/OIDC login flow in Next.js, session refresh/revocation, browser CSRF protection, MFA/SSO, actual two human accounts, redacted ticket/evidence views, IP rate limiting, audit immutability policy and threat model review before end-user release. Real pairwise incident precision/F1 remains unknown without annotated support tickets.
