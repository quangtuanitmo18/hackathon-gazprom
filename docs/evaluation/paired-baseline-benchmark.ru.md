# Проверяемый pilot-протокол: ручной процесс A vs rules/BM25 B vs Hybrid Qwen C

**Статус: ПРЕДЛОЖЕНИЕ, НЕ ИЗМЕРЕНИЕ.** Не запускались внутренние Qwen, не получены реальные тикеты/аудио, не размечен gold set; 7 Webneft-текстов PDF — не gold. Цель: спроектировать эксперимент, способный **опровергнуть** необходимость более сложной системы C.

## 0. Процесс A, модель B и модель C на одном масштабе

- **A — действующий ручной процесс**, выяснить, что уже делает техподдержка. Baseline: время аналитики, доля запросов, дошедших до product team, подтвержденные бизнес-решения, полнота и SLA; не заявлять, что сейчас процесс отсутствует.
- **B — allowlisted rules + BM25** на очищенных text/ticket metadata, детерминированный product routing и internal digest. Это технический baseline и допустимый fallback.
- **C — те же права/коды и backend правила**, плюс Qwen-ASR/VL/текст для *семантики* (парафразы, речь, вложения), строго внутренний egress. LLM не может создавать ticket IDs, считать recurrence, менять учетные записи или принимать финальные решения.

Общий вход: разрешенные авторизованные источники; **одинаковые** `source_id`, `product_id`, temporal-window и `source_coverage`, одно окно времени и политика PII. Обработанные данных не должны быть доступны из будущего. Для сравнения A ретроспектива должна иметь реальные журналированные действия, иначе берется prospective time study и результат считается предварительным.

## 1. Подготовка gold и срезов

1. Стратификация по нескольким разрешенным продуктам, каналам (ticket, call, image), частым/редким темам, срочности, `unknown`, abstain и изменениям сезонности. Pilot в одном продукте НЕ обосновывает вывод на десятки.
2. Зафиксировать holdout по **времени и продуктам**; не выбирать train/taxonomy dictionary на основе holdout и не «раскрывать» будущие тикеты при формировании кандидатов.
3. Два независимых слепых аннотатора + арбитр размечают **intent, business journey, actionable, same-problem pair, route** и наличие достаточного evidence. Зафиксировать disagreement, label guide, reconciliation, PII policy.
4. Сохранять исходные source IDs только в защищённой инфраструктуре; публичный отчёт содержит обезличенные агрегаты. При неизвестном `source_coverage` не утверждать полную частоту и рост.

## 2. Метрики и точный decision rule

| Цель | Как считать | Ограничения |
|---|---|---|
| Actionable precision выбранных к отправке сигналов | `TP/(TP+FP)`, по экспертной случайной/взвешенной выборке **включая неreviewed** | Показывать `n, TP, FP`, 95% Wilson CI, sampling weights, effective n; не подменять product acceptance |
| Routing accuracy и coverage | correct adjudicated / attempted, **и** auto-routed / all eligible | Нет registry→human, не выбрасывать `unknown` из coverage |
| Recurring recall и false-merge rate | Разметка **всей** релевантной популяции окна, отдельные `same_problem_pair` | Никакой импликации «похожая тема → один инцидент» |
| TPI / E2E / undelivered | `qualified_at→sent_at` отдельно от `first_relevant_ingested_at→sent_at` + недоставленные, возраст backlog, missing clocks | Delivered-only p90 без backlog вводит в заблуждение |
| Net reviewer/support minutes | Учесть время аналитики, проверки и исправления AI; интервалы неопределённости | Минуты не означают денежную экономию автоматически |
| Дополнительная полезность C−B | Разность независимых **полезных уникальных сигналов**, clean manual minutes, recall и false merges на том же holdout | Определить non-inferiority safety и приемлемые life-cycle затраты до эксперимента |

**Иллюстрация планирования выборки:** при предполагаемой `p≈0.8` и желаемой абсолютной погрешности `e=0.05`, `n≈(1.96²×0.8×0.2)/(0.05²)=245.86≈246` независимых размеченных кандидатов. Это приближённая **оценка точности**, НЕ размер, гарантирующий PASS. Для примера 200/250=0.800 ⇒ нижняя 95% Wilson ≈0.746 (**не PASS** по строгому критерию), а 213/250=0.852 ⇒ нижняя ≈0.803. Стратификация/кластеризация/редкие классы меняют необходимое n.

**Предлагаемый, но не утвержденный business owner GO gate:** нижняя граница 95% Wilson для истинной actionable precision≥0.80 (при корректном дизайне/весах), routing≥0.95 + достаточная coverage; 0 разрешенных PII/egress нарушений в tests; неизменный urgent SLA; подтвержденная дополнительная ценность C над B. **Важно:** если p=0.80 в наблюдении, нижняя CI обычно ниже .80 — условие не выполняется. Можно выбрать другой бизнес-acceptable criterion после согласования; не подгонять порог post hoc.

**Парное сравнение B/C:** одинаковые holdout units и ручные метки; paired differences в доле полезных сигналов, precision/recall и net labor, доверительные интервалы бутстрепом по независимым `product×week`/incident clusters, а не по коррелированным ASR-фрагментам. Для сравнения с A и фактического экономического эффекта — matched/control rollout с учетом сезонности и объема.

## 3. Decision table — что будет считаться доказательством

| Наблюдение после реального pilot | Решение |
|---|---|
| C дает больше **независимо подтвержденных** полезных тем и меньше net manual minutes, без ухудшения safety/SLA; PV инкрементальной ценности > PV инкрементальных затрат | Рассмотреть ограниченный rollout C; не называть компанию уже внедрившей |
| B≈C по полезности и false merges при меньшей сложности | Предпочесть B; AI не является самоцелью |
| C имеет более высокую recall, но низкую precision/много wrong-team alerts | Вернуть C в shadow, улучшить taxonomy/prompts; автоматическую доставку заблокировать |
| Недостаточная выборка/неполные timestamps/недоступен gold | Решение `NOT VERIFIED`, manual/B only; не публиковать придуманную точность |

**Текущий факт:** ни одна строка результатов реального эксперимента не заполнена. Семь кейсов PDF могут служить качественными тест-сценариями; три SYN-QUEUE — исключительно вымышленный демонстрационный пример.
